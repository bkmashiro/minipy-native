目标：一次性 Agent Python-like 脚本，从新源码到结果的总成本尽可能低，同时降低大量并发任务的等待内存和短任务延迟。代码通常只跑一次，不能默认靠代码缓存、重复执行或长循环摊销编译。追求少做工作、少拷贝、少初始化、紧凑状态与静态绑定。可以牺牲部分 Python 动态语义，仍希望保留 LLM 熟悉的自然语法。

当前已有：RustPython 前端、共享 typed IR、紧凑 tape 解释器、Cranelift native；Host 声明 Tool/schema；同步写法内部异步挂起；连续数据借用、末次使用释放；opt-in JSON 按字段读取与窄字符串 contains、共享 HTTP 客户端。类 eBPF 的启发是受限语言和执行前校验，实际运行在用户态宿主进程内，编译器/runtime/provider 属于 TCB。请自行核对实现，不把目标当成已经实现。

请重点研究：

1. schema 的扩展成本。
固定宽度记录 schema 已知，字段、偏移和操作类型应能在准备期绑定。AY 实验却让旧 Quote tape warm 路径明显变慢；拆分扫描入口后一次配对仍约 +50.7%。目前未集成。为什么 Cargo opt-in 开启后，一个不使用新增功能的程序仍可能付出这种成本？检查 Op enum 大小、指令密度、读取逻辑、State/Frame 布局、匹配分派、内联、寄存器压力和 cache 行为，也审查实验混杂。
请区分编译器自身 AOT、部署时 schema 准备、用户程序准备、逐行执行四个阶段。哪些工作应该在哪一层完成？如何让新增类型和 schema 特化不污染旧快路，同时避免复制两套编译器或组合爆炸？请给出具体代码位置和最小消融方案，不能仅用“动态分派慢”解释。

2. Tool / HTTP 成本。
读 AL 与 BE：I/O driver 下 detached operation + oneshot + deferred yield 组合有额外成本，event_interval 调整与 JoinHandle 替换均未产生稳定总体收益。哪些分配、任务创建、通知或调度跳转可被删除/合并？能否在完成路径、ready 路径或借用生命周期上简化？必须保留真正异步、取消后迟到操作的资源归属、错误和外部副作用语义、计算公平性。若更激进设计需要改变这些契约，请明确代价，不要悄悄删掉语义。也可以判断收益不足，应停止优化这里。

3. 解释、编译与预编译 kernel 的平衡。
整体目标是压低“准备 + 执行”，同时改善多任务群体行为。研究：更便宜的解释器表示；部署时预编译的通用 kernel；解释编排 + native 扫描；只编译实际走到且剩余工作足够多的路径；低成本整任务选择。不要预设一定需要 JIT，也不要预设换后端。我们允许有新意的局部重设计，但新增选择、检测、编译、安装、状态交接和内存保活成本必须能回本。
对于局部编译，说明自然边界、如何传递 locals/index/预算/owner/输出，怎样避免重发 Tool、重复处理数据或错误后重新解释。对于 kernel，找高频且可通用复用的操作，避免为 benchmark 业务逻辑定制答案。请比较最强简单替代，如直接借用成熟 Rust 库、保持显式后端选择。

4. JSON 和实用语言能力。
当前借用原始 bytes、静态字段路径、按需解码的边界是否合理？多字段读取、重复路径、字符串/子视图、数组遍历如何减少重复扫描而不过早构造 DOM？何时少量复制优于保活大 buffer？考虑未访问非法尾部、重复 key、转义字符串等当前语义；若建议改语义请明确。区分 typed upstream 的直接访问与普通 JSON 必须完成的定位/解析工作。怎样扩展必要能力而让不用它的程序基本不付费？
